# Ansible: возможности, компоненты и best practices

`Ansible` — инструмент автоматизации для:

* управления конфигурациями
* деплоя приложений
* оркестрации инфраструктуры

Основная идея — описание **желаемого состояния системы (desired state)**.

## Преимущества

- Agentless (без агентов)
- Использует SSH
- YAML (читаемый формат)
- Идемпотентность
- Быстрый старт

## Основные компоненты

Ansible состоит из набора логических компонентов, каждый из которых отвечает за определённую часть автоматизации.

### 1) Control Node

Управляющая машина, на которой установлен Ansible.

Именно отсюда:
- запускаются playbook
- выполняются команды
- происходит подключение к удалённым хостам

### 2) Managed Nodes

Удалённые хосты, которые настраиваются Ansible.

Особенности:
- не требуют установки Ansible
- достаточно SSH-доступа и Python (в большинстве случаев)
- могут быть как физическими серверами, так и VM или контейнерами

### 3) Inventory

Файл или набор файлов, описывающих инфраструктуру.

Позволяет:
- группировать хосты
- задавать переменные
- управлять окружениями

Пример:
```ini
[web]
web1 ansible_host=192.168.1.10

[db]
db1 ansible_host=192.168.1.20
```

Inventory может быть:
- статическим (ini/yaml)
- динамическим (например, из cloud API)

### 4) Modules

Базовые строительные блоки Ansible.

Это небольшие программы, которые выполняют конкретные действия:
- установка пакетов
- управление файлами
- работа с сервисами

Примеры:
- apt, yum — управление пакетами
- copy, template — работа с файлами
- service — управление сервисами

Модули:
- идемпотентны
- выполняются на удалённой машине
- возвращают результат в структурированном виде

### 5) Playbook

Основной способ описания автоматизации.

Это YAML-файл, в котором:
- задаются хосты
- описываются задачи
- определяется порядок выполнения

Пример:
```yaml
- hosts: web
  become: true
  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present
```

### 6) Tasks

Отдельные шаги внутри playbook.

Каждая задача:
- вызывает один модуль
- выполняет одно действие
- имеет имя (не обязательно, но рекомендуется)

Пример:
```yaml
- name: Install nginx
  apt:
    name: nginx
    state: present
```

### 7) Roles

Механизм структурирования и переиспользования кода.

Роль объединяет:
- задачи
- шаблоны
- переменные
- обработчики

Типичная структура:
````
roles/
  nginx/
    tasks/
    handlers/
    templates/
    vars/
    defaults/
````

Позволяет:
- разбивать сложные сценарии
- переиспользовать код
- поддерживать чистую архитектуру

### 8) Handlers

Специальные задачи, которые выполняются только при изменениях.

Обычно используются для:
- перезапуска сервисов
- применения конфигурации

Пример:
```yaml
- name: restart nginx
  service:
    name: nginx
    state: restarted
```

Вызываются через notify из задач.

### 9) Variables

Позволяют делать playbook гибкими.

Могут задаваться:
- в inventory
- в playbook
- в group_vars / host_vars
- через CLI

Поддерживают приоритеты и переопределение.

### 10) Facts

Автоматически собираемая информация о системе:
- ОС
- IP-адреса
- ресурсы (CPU, RAM)

Используются для:
- условий
- динамической настройки

### 11) Templates (Jinja2)

Используются для генерации конфигурационных файлов.

Позволяют:
- подставлять переменные
- использовать условия и циклы

Пример:
```yaml
server_name {{ domain }};
```

## Как работает Ansible

На базовом уровне Ansible выполняет задачи на удалённых хостах следующим образом:

1. Устанавливает SSH-соединение с хостом
2. Передаёт модуль (временный код)
3. Выполняет его на удалённой машине
4. Удаляет после выполнения

Главная ценность Ansible — не в этих шагах, а в том, что он позволяет:

#### 1. Управлять инфраструктурой как кодом

Вместо ручной настройки серверов ты описываешь их состояние в YAML-файлах.

Это даёт:
- повторяемость
- контроль версий
- возможность отката

#### 2. Автоматизировать рутинные задачи
Любая операция:
- установка пакетов
- настройка сервисов
- деплой приложения

выполняется автоматически и одинаково на всех серверах.

#### 3. Обеспечивать консистентность среды
Все серверы приводятся к одному состоянию.

Это решает классическую проблему:
"у меня на машине работает, а на сервере нет".

#### 4. Масштабировать инфраструктуру
Один и тот же playbook можно применить:
- к одному серверу
- к десяткам
- к сотням

без изменения кода.

#### 5. Снижать количество ошибок
Человеческий фактор минимизируется:
- нет ручного ввода команд
- нет забытых шагов
- нет расхождений между серверами

## Best Practices

#### 1. Декларативный подход (desired state)
Ansible описывает желаемое состояние системы, а не последовательность команд.

Плохо:
```yaml
command: apt install nginx -y
```

Хорошо:
```yaml
apt:
  name: nginx
  state: present
```

Это делает поведение playbook предсказуемым и безопасным при повторных запусках.

#### 2. Идемпотентность

Playbook должен давать одинаковый результат при любом количестве запусков.

Используй встроенные модули вместо shell/command, так как они уже обеспечивают идемпотентность.

#### 3. Декомпозиция через роли

Не стоит писать один большой playbook.

Правильный подход:
- одна роль — одна зона ответственности
- роли переиспользуются
- структура становится понятной

#### 4. Разделение кода и данных

Не хардкодь значения внутри задач.

Плохо:
```yaml
port: 80
```

Хорошо:
```yaml
port: "{{ nginx_port }}"
```

Это позволяет использовать один и тот же код в разных окружениях.

#### 5. Структура проекта

Даже небольшой проект должен иметь понятную структуру:

````
inventory/
group_vars/
host_vars/
roles/
playbooks/
````

Без структуры проект быстро становится трудно поддерживаемым.

#### 6. Разделение окружений

Используй разные inventory для разных сред:
````
inventory/
  dev/
  prod/
````
Это снижает риск ошибок в production.

#### 7. Использование handlers

Перезапуск сервисов должен происходить только при изменениях.
Это уменьшает нагрузку и делает выполнение playbook быстрее и безопаснее.

#### 8. Минимизация shell и command

Эти модули:
- не идемпотентны
- сложнее в поддержке
- ухудшают читаемость

Используй специализированные модули whenever possible.

9. Маленькие и понятные задачи

Одна задача должна выполнять одно действие.

Плохо:
```yaml
- name: setup server
```

Хорошо:
```yaml
- name: Install nginx
- name: Configure nginx
- name: Start nginx
```

Это упрощает отладку и сопровождение.

#### 10. Использование тегов

Позволяет запускать только нужные части playbook.
```yaml
tags: nginx
```

Запуск:
```bash
ansible-playbook playbook.yaml --tags nginx
```

#### 11. Проверка перед выполнением

Используй режим dry-run:
```bash
ansible-playbook playbook.yaml --check
```

Это помогает обнаружить ошибки до реального применения.

#### 12. Работа с секретами через Vault

Не храни чувствительные данные в открытом виде.
```bash
ansible-vault encrypt vars.yaml
```

#### 13. Использование lint и тестирования

Рекомендуемые инструменты:
- ansible-lint
- molecule

Это повышает качество кода и снижает количество ошибок.

#### 14. Контроль использования become

Используй повышение привилегий только там, где это необходимо.

Это уменьшает риски безопасности.

#### 15. Принцип DRY (Don't Repeat Yourself)

Избегай дублирования:
- переменных
- задач
- конфигураций

Используй роли, шаблоны и includes.

#### 16. Читаемость как приоритет

Playbook должен быть понятен без дополнительного объяснения.

Хороший код:
- легко читается
- логично структурирован
- описывает происходящее шаг за шагом
