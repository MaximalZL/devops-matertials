# Kubernetes Overview: архитектура, Control Plane и Data Plane

## 1. Что такое Kubernetes простыми словами
Kubernetes (k8s) — это система оркестрации контейнеров. Она нужна, чтобы **автоматически запускать, масштабировать, обновлять и восстанавливать** приложения, упакованные в контейнеры.

Главная идея Kubernetes: мы описываем **желаемое состояние** (desired state), а кластер постоянно приводит фактическое состояние к этому описанию.

Пример:
- хотим 3 экземпляра приложения;
- один контейнер упал;
- Kubernetes сам создаст новый, чтобы снова стало 3.

---

## 2. Архитектура: из чего состоит кластер
У Kubernetes два больших слоя:

1. **Control Plane** — «мозг» кластера
Что должно быть запущено, где, в каком количестве, с какими правилами.

2. **Data Plane** (worker-ноды) — «рабочие руки»
Где реально крутятся контейнеры, ходит трафик и используются ресурсы CPU/RAM/Disk/Network.

Коротко:
- Control Plane принимает решения.
- Data Plane выполняет решения.

---

## 3. Control Plane: компоненты подробно

## `kube-apiserver`
Это центральная точка входа в кластер.

Что делает:
- принимает команды от `kubectl`, CI/CD, операторов, контроллеров;
- проводит аутентификацию (кто ты);
- проводит авторизацию (что тебе можно);
- запускает admission-плагины (дополнить/проверить запрос);
- сохраняет/читает объекты через `etcd`.

Важно:
- почти все взаимодействия в кластере идут через API Server;
- это “front door” Kubernetes.

## `etcd`
Распределенное key-value хранилище состояния кластера.

Что хранится в etcd:
- Deployment, Service, Pod, Secret, ConfigMap и другие API-объекты;
- текущее и желаемое состояние;
- метаданные (resourceVersion, UID и т.д.).

Почему critical:
- потеря etcd = потеря состояния кластера;
- для production важны бэкапы etcd и контроль кворума.

## `kube-scheduler`
Планировщик, который выбирает ноду для Pod.

На что смотрит:
- доступные ресурсы (CPU, RAM, ephemeral storage);
- `nodeSelector`, `nodeAffinity`, `podAffinity/antiAffinity`;
- `taints`/`tolerations`;
- topology spread constraints;
- портовые и другие ограничения.

Важный момент:
- scheduler **не запускает** контейнер сам;
- он только принимает решение и пишет `nodeName` в Pod.

## `kube-controller-manager`
Набор контроллеров, которые постоянно сравнивают desired и actual state.

Примеры контроллеров:
- **Deployment Controller**: следит за rollout;
- **ReplicaSet Controller**: поддерживает нужное число Pod;
- **Node Controller**: отслеживает состояние нод;
- **Job/CronJob Controller**;
- **EndpointSlice Controller** и др.

Принцип работы:
- цикл reconcile: “посмотрел текущее состояние -> увидел расхождение -> сделал действие”.

## `cloud-controller-manager` (если облако)
Нужен, когда кластер работает в облаке.

Что обычно делегируется облаку:
- создание внешних Load Balancer;
- привязка persistent-дисков;
- интеграция с облачной сетью и IP.

## 4. Data Plane: компоненты подробно

## Worker Node
Worker-нода — это сервер/VM, где фактически работают Pod.

На каждой worker-ноде обычно есть:
- `kubelet`;
- container runtime (`containerd` или `CRI-O`);
- сетевой dataplane (`kube-proxy` или eBPF-реализация CNI);
- CNI-компоненты.

## `kubelet`
Агент ноды, который общается с API Server.

Что делает:
- получает спецификацию Pod, назначенных на эту ноду;
- через CRI просит runtime создать/запустить контейнеры;
- подключает тома (через CSI при необходимости);
- запускает probes (`startup/liveness/readiness`);
- отправляет статус Pod/Node обратно в API.

Важно:
- kubelet — главный исполнитель на ноде.

## Container Runtime (`containerd` / `CRI-O`)
Компонент, который реально запускает контейнерные процессы.

Отвечает за:
- pull образов;
- создание container sandbox;
- запуск/остановку контейнеров;
- сбор stdout/stderr логов.

Через что интегрирован:
- через CRI (Container Runtime Interface).

## Сетевой плагин (CNI)
Kubernetes не навязывает одну сетевую реализацию.

CNI-плагин отвечает за:
- выдачу IP Pod;
- настройку маршрутов и связности Pod-to-Pod;
- работу overlay/underlay сети;
- (часто) NetworkPolicy.

Популярные варианты:
- Calico;
- Cilium;
- Flannel (более простой);
- Weave Net и др.

## `kube-proxy` (или его замена)
Реализует сервисную сетевую абстракцию на ноде.

Что делает:
- настраивает правила маршрутизации для Service;
- направляет трафик на актуальные Pod backend;
- обычно через iptables или IPVS.

Важно:
- в некоторых кластерах kube-proxy заменяется eBPF dataplane (например, Cilium).

## 5. Как запрос проходит по системе (жизненный цикл)
Пример: выполняем `kubectl apply -f deployment.yaml`.

1. `kubectl` отправляет объект в `kube-apiserver`.
2. API Server: authn/authz + admission checks.
3. Объект сохраняется в `etcd`.
4. `Deployment Controller` создает/обновляет ReplicaSet.
5. ReplicaSet создает Pod.
6. Scheduler выбирает ноду для Pod.
7. Kubelet на этой ноде через runtime запускает контейнер.
8. CNI настраивает сеть, Pod получает IP.
9. Readiness probe становится `OK`.
10. Service/EndpointSlice обновляются, трафик начинает идти в Pod.

Итог: из декларации (YAML) получаем рабочий экземпляр приложения.

## 6. Надежность и отказоустойчивость

Почему Kubernetes устойчив к сбоям:
- реплики приложения (ReplicaSet);
- самовосстановление Pod;
- health probes;
- независимость нод;
- HA Control Plane (обычно 3+ control-plane узла);
- кворум etcd.

Типовые сценарии:
- упал Pod -> создается новый;
- нода `NotReady` -> Pod пересоздаются на других нодах (если хватает ресурсов);
- упал один control-plane узел в HA-кластере -> управление продолжает работать.

---

## 7. Что обязательно понимать инженеру

1. Kubernetes — система **декларативного управления**.
2. Control Plane принимает решения, Data Plane их исполняет.
3. `kube-apiserver` + `etcd` — критическое ядро.
4. Контроллеры работают в цикле reconcile, а не “один раз”.
5. Без CNI сеть Pod не заработает.
6. Service скрывает эфемерность Pod и дает стабильную точку доступа.

## 8. Краткая шпаргалка по компонентам

### Control Plane
- `kube-apiserver` — API и входная точка.
- `etcd` — хранилище состояния.
- `kube-scheduler` — выбор ноды.
- `kube-controller-manager` — контроль и самовосстановление.
- `cloud-controller-manager` — интеграция с облаком.

### Data Plane
- `kubelet` — агент ноды и исполнитель.
- `container runtime` — запуск контейнеров.
- `CNI` — сеть Pod.
- `kube-proxy`/eBPF — сервисная маршрутизация.

---

## 9. Почему это удобно в реальной работе
Kubernetes снимает рутину эксплуатации:
- автоматический перезапуск и пересоздание;
- безопасные rollout/rollback;
- масштабирование без ручной возни;
- единая модель управления для разных сред (dev/stage/prod).

Поэтому в реальных командах Kubernetes ценят не за “модность”, а за предсказуемую эксплуатацию и уменьшение ручных ошибок.
