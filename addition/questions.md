# Дополнительные вопросы

## 1) С помощью чего можно собрать информацию о текущем состоянии диска и/или сети?

Ниже рабочий подход: сначала быстро локализуем проблему, потом уточняем причину.

### Диск: что смотреть в первую очередь
- `df -h` — заполнение файловых систем.
- `df -i` — проверка, не закончились ли inode (частая причина “No space left on device” при свободных гигабайтах).
- `du -xhd1 /path` — кто занимает место внутри конкретной точки монтирования.
- `lsblk -f` — диски, разделы, ФС, UUID, точки монтирования.
- `iostat -xz 1` — задержки и утилизация диска в динамике.
- `iotop` — какие процессы сейчас дают основной I/O.
- `smartctl -a /dev/sdX` — состояние диска по SMART.

Как интерпретировать `iostat`:
- высокий `await` + высокий `%util` - диск перегружен;
- низкий `%util`, но высокий `await` - возможна проблема очередей/контроллера/виртуализации;
- стабильный рост `avgqu-sz` - запросов больше, чем диск успевает обработать.

Быстрый набор команд:
```bash
df -h
df -i
du -xhd1 /var 2>/dev/null | sort -h
iostat -xz 1
```

### Сеть: что смотреть в первую очередь
- `ip a` — интерфейсы и адреса.
- `ip route` — маршруты и дефолтный gateway.
- `ss -tulpen` — слушающие порты и процессы.
- `ss -s` — общий срез по TCP-состояниям.
- `ping`, `tracepath`/`traceroute` — связность и путь.
- `dig`/`resolvectl query` — DNS-резолвинг.
- `iftop`/`nload` — оперативная картина по трафику.
- `tcpdump` — пакетный уровень для точечной диагностики.
- `ethtool eth0` — скорость линка, дуплекс, ошибки.

Быстрый набор команд:
```bash
ip a
ip route
ss -tulpen
ss -s
```

## 2) Как поднять приоритет процесса?

В Linux есть три разных механизма, и они решают разные задачи.

### 1. CPU-приоритет (`nice` / `renice`)
`nice` влияет на планировщик CFS:
- диапазон: `-20` (выше приоритет) ... `19` (ниже приоритет);
- изменить уже запущенный процесс: `renice`.

```bash
nice -n -10 ./app
renice -n -10 -p <PID>
```

### 2. Real-time планирование (`chrt`)
Для задач с жесткими требованиями по задержкам:
- `SCHED_FIFO`, `SCHED_RR`;
- приоритет RT обычно 1..99.

```bash
chrt -f 50 ./app
chrt -p <PID>
```

### 3. I/O-приоритет (`ionice`)
Если узкое место — диск, а не CPU:
```bash
ionice -c2 -n0 -p <PID>
```

Проверка текущих параметров процесса:
```bash
ps -o pid,ni,pri,cls,rtprio,comm -p <PID>
```

Рекомендации:
- начинаем с умеренных изменений (`nice -5`, `ionice`), а не с экстремальных значений;
- RT-приоритет выставляем только если понимаем последствия для всей системы;
- отрицательные `nice` и RT-настройки обычно требуют root.

## 3) Чем отличается системное время от пользовательского времени?

Когда запускаем процесс через `time`, получаем три времени:
- `real` — прошло по обычным часам;
- `user` — CPU-время в user space;
- `sys` — CPU-время в kernel space (системные вызовы).

```bash
time ./app
```

Как читать результат:
- высокий `user`, низкий `sys` -> процесс в основном считает (CPU-bound);
- высокий `sys` -> много системных вызовов: I/O, сеть, файловые операции, копирование памяти;
- высокий `real` при низких `user+sys` -> процесс в основном ждет (диск, сеть, блокировки, внешние сервисы).

Нюанс:
- на многоядерной машине `user + sys` может быть больше `real`, это нормально;
- например, `real=10s`, `user=30s` означает, что суммарно было занято около 3 CPU-ядер.

## 4) Какие есть файловые системы? Зачем они нужны? Когда какую выбирать?

Файловая система определяет:
- как данные пишутся и читаются;
- как хранится метаинформация и права;
- как ведется журнал;
- есть ли снапшоты, checksums, CoW и встроенные механизмы восстановления.

### Часто используемые ФС
- `ext4` — надежная универсальная ФС общего назначения.
- `XFS` — хорошо масштабируется на больших томах и высокой параллельной нагрузке.
- `Btrfs` — CoW, снапшоты, subvolume, send/receive.
- `ZFS` — checksums, снапшоты, RAID-like пул, репликация, высокая защита целостности данных.
- `tmpfs` — хранение в RAM (быстро, но данные исчезают после перезагрузки).

### Как выбирать
- универсальный сервер без специальных требований: `ext4`;
- большие объемы и интенсивный поток данных: `XFS`;
- нужны снапшоты и удобные rollback-сценарии: `Btrfs`/`ZFS`;
- критична целостность и контроль хранения на уровне пула: скорее всего `ZFS`;
- временные файлы, cache, runtime-артефакты: `tmpfs`.

### Что учитывать дополнительно
- совместимость с дистрибутивом и инструментами бэкапа;
- сложность администрирования команды (например, ZFS/Btrfs требуют опыта);
- стоимость восстановления и простота операций на проде.

## 5) Что такое I-ноды?

`inode` — это запись о файле с метаданными, но без имени файла.

В inode хранятся:
- тип файла;
- права и режим;
- UID/GID;
- размер;
- `atime`, `mtime`, `ctime`;
- ссылки на блоки данных;
- счетчик hard link.

Важные следствия:
- имя файла хранится в каталоге, который ссылается на inode;
- hard link — это еще одна ссылка на тот же inode;
- файл удаляется физически только когда счетчик ссылок = 0 и процесс не держит его открытым;
- можно исчерпать inode раньше, чем место на диске (типично для огромного числа мелких файлов).

Диагностика:
```bash
df -i
ls -li
lsof | grep '(deleted)'
```

## 6) Что такое зомби-процесс и сирота-процесс?

### Зомби (Zombie)
Процесс завершился, но родитель не вызвал `wait()`/`waitpid()`, поэтому запись о процессе остается в таблице процессов.

Признаки:
- статус `Z`/`defunct`;
- CPU и память почти не потребляет, но занимает PID и “засоряет” процессную таблицу.

Проверка:
```bash
ps -el | grep ' Z '
```

Что делать:
- исправить код родителя (обработка SIGCHLD и `waitpid`);
- перезапустить родительский процесс, если это допустимо.

### Сирота (Orphan)
Родительский процесс завершился, а дочерний остался жить. Дочерний процесс переназначается `init/systemd` и продолжает работу.

Это штатный механизм Linux и сам по себе не ошибка.

## 7) Как ограничивать процесс по памяти? (cgroups, systemctl)

На современных системах правильно ограничивать память через cgroups v2 и systemd.

### Временный запуск
```bash
systemd-run --scope -p MemoryMax=500M ./app
```

### Для постоянного сервиса
В unit-файле:
```ini
[Service]
MemoryHigh=400M
MemoryMax=500M
OOMPolicy=kill
```

Применение:
```bash
sudo systemctl daemon-reload
sudo systemctl restart myapp
```

Смысл лимитов:
- `MemoryHigh` — мягкий порог (начинается reclaim/throttling);
- `MemoryMax` — жесткий лимит (при превышении возможен OOM kill).

Проверка:
```bash
systemctl show myapp -p MemoryCurrent -p MemoryPeak -p MemoryMax -p MemoryHigh
systemd-cgtop
```

Замечание:
- `ulimit -v` и похожие методы существуют, но обычно хуже контролируются и уступают cgroups.

## 8) Что такое DNS и какие типы записей существуют?

DNS — распределенная иерархическая система преобразования имен в IP и хранения сервисных записей.

Цепочка запроса обычно такая:
1. приложение -> stub resolver на хосте;
2. локальный/корпоративный рекурсивный резолвер;
3. авторитативные DNS-сервера зоны;
4. ответ кэшируется по TTL.

### Основные типы DNS-записей
- `A` — имя -> IPv4.
- `AAAA` — имя -> IPv6.
- `CNAME` — псевдоним на другое имя (не на IP).
- `MX` — почтовые серверы домена.
- `TXT` — SPF, DKIM, DMARC, верификации.
- `NS` — авторитативные серверы зоны.
- `SOA` — параметры зоны (serial, retry, refresh).
- `PTR` — обратная зона (IP -> имя).
- `SRV` — сервис + порт + приоритет.
- `CAA` — какие CA имеют право выпускать сертификаты.

### Типы DNS-серверов
- рекурсивный резолвер — ищет ответы за клиента;
- авторитативный DNS — источник записей конкретной зоны.

Проверка на практике:
```bash
dig +short A example.com
dig +trace example.com
dig MX example.com
```

## 9) Как конкретному пользователю дать права на файлы? Как решать конфликты портов?

### Права на файлы

Базовые инструменты:
- `chown` — владелец и группа;
- `chmod` — режим доступа;
- ACL (`setfacl`) — точечные права конкретным пользователям.

Примеры:
```bash
sudo chown user1:devs /srv/app/config.yml
sudo chmod 640 /srv/app/config.yml
sudo setfacl -m u:user2:r /srv/app/config.yml
getfacl /srv/app/config.yml
```

Для общих рабочих каталогов полезно:
- выставить группу каталога;
- включить `setgid` на директории, чтобы новые файлы наследовали группу;
- добавить default ACL.

```bash
sudo chgrp -R devs /srv/project
sudo chmod 2775 /srv/project
sudo setfacl -m d:g:devs:rwx /srv/project
```

### Конфликты портов

Алгоритм:
1. Найти, кто слушает порт.
2. Решить: освобождаем порт или меняем конфиг сервиса.
3. Проверить после изменений.

```bash
ss -ltnp | grep :8080
sudo lsof -i :8080
sudo systemctl status <service>
sudo systemctl stop <service>
```

После правки конфигурации:
```bash
sudo systemctl restart <service>
ss -ltnp | grep :8080
```

## 10) Git: merge, rebase, fetch, pull, squash commit, VCS. Как откатывать коммиты?

### Ключевые команды
- `git fetch` — обновить удаленные ссылки (`origin/*`), не меняя текущую ветку.
- `git pull` — `fetch` + интеграция (`merge` или `rebase`).
- `merge` — объединение веток с сохранением структуры истории.
- `rebase` — перенос коммитов на новую базу с переписыванием истории.
- `squash` — объединение нескольких коммитов в один.

### Когда использовать
- `fetch`: перед анализом изменений и ревью чужих коммитов.
- `merge`: для shared-веток, где историю переписывать нельзя.
- `rebase`: для личной feature-ветки до публикации.
- `pull --rebase`: чтобы не плодить merge-коммиты в рабочей ветке.
- `squash`: чтобы сделать чистый PR-коммит из нескольких промежуточных.

### Откат коммитов

Безопасный откат в общей ветке:
```bash
git revert <commit>
git revert -m 1 <merge_commit>
```

Локальный откат последнего коммита:
```bash
git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
```

Восстановление после неудачного `reset/rebase`:
```bash
git reflog
git reset --hard <hash_from_reflog>
```

Полезная проверка перед рискованными действиями:
```bash
git status
git log --oneline --graph --decorate -20
```

## 11) Linux Signals

Signal — асинхронное событие для процесса от ядра или другого процесса.

### Основные сигналы
- `SIGTERM (15)` — корректное завершение, процесс может выполнить cleanup.
- `SIGKILL (9)` — мгновенное завершение без cleanup, не перехватывается.
- `SIGINT (2)` — прерывание из терминала (`Ctrl+C`).
- `SIGHUP (1)` — часто “перечитай конфиг”, но это зависит от приложения.
- `SIGQUIT (3)` — завершение с core dump (если включено).
- `SIGSTOP`/`SIGCONT` — пауза/продолжение процесса.

### Рекомендуемый порядок действий
1. Отправить `SIGTERM`.
2. Подождать и проверить состояние процесса.
3. Только если процесс завис, отправить `SIGKILL`.

Примеры:
```bash
kill -TERM <PID>
kill -0 <PID>     # проверка: жив ли процесс
kill -9 <PID>
pkill -f "myapp"
```

Для shell-скриптов:
```bash
trap 'echo "cleanup"; rm -f /tmp/my.lock' EXIT INT TERM HUP
```

Важно:
- перехватить нельзя `SIGKILL` и `SIGSTOP`;
- при работе под systemd лучше сначала использовать `systemctl stop`, а не `kill`, если процесс — сервис.

## 12) Soft link, hard link. Какие "линки" в Linux существуют?

В Linux в контексте файлов обычно говорят о двух типах ссылок: hard link и symbolic link.

### Hard link
- еще одно имя того же inode;
- работает только в пределах одной файловой системы;
- обычно не применяется к директориям;
- файл реально исчезнет только когда счетчик ссылок станет 0.

```bash
ln file.txt file_hardlink.txt
ls -li file.txt file_hardlink.txt
```

### Symbolic link (soft link)
- отдельный inode, внутри хранится путь к цели;
- может ссылаться на другой раздел и даже на несуществующий путь;
- при удалении/перемещении цели становится битой ссылкой.

```bash
ln -s /path/to/target my_link
ls -l my_link
readlink -f my_link
```

Практическое правило:
- hard link — когда важна “привязка к данным” на том же ФС;
- symlink — когда нужна гибкость по путям и структуре каталогов.

## 13) Выпуск сертификатов: как скачать с сервера сертификат через openssl, как выпустить сертификат и т.п.

### Получить сертификат с удаленного сервера
```bash
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null
```

Сохранить leaf-сертификат:
```bash
openssl s_client -connect example.com:443 -servername example.com </dev/null \
  | openssl x509 -outform PEM > server.crt
```

Проверить:
```bash
openssl x509 -in server.crt -noout -subject -issuer -dates -ext subjectAltName
```

### Выпуск сертификата (общий процесс)
1. Сгенерировать приватный ключ:
```bash
openssl genrsa -out server.key 2048
```

2. Подготовить CSR (обязательно с SAN):
```bash
openssl req -new -key server.key -out server.csr
```

3. Отправить CSR в CA (внутренний или публичный).
4. Получить сертификат и цепочку, настроить на сервисе (`nginx`, `apache`, `haproxy`).
5. Проверить цепочку и сроки действия.

Проверка цепочки:
```bash
openssl verify -CAfile ca_bundle.crt server.crt
```

### Тестовый self-signed сертификат
```bash
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout selfsigned.key -out selfsigned.crt -days 365
```

Практические требования безопасности:
- приватный ключ (`*.key`) хранить с правами `600` и вне публичных репозиториев;
- регулярно проверять срок действия сертификатов;
- на проде автоматизировать продление (например, `certbot` + systemd timer/cron);
- после продления проверять, что сервис перезагружен и отдает новый сертификат.

## Подходы DevOps, DRY, KISS и др.

### DevOps как подход
DevOps — это совместная ответственность разработки и эксплуатации за весь цикл: от кода до стабильной работы в проде.

Ключевая идея:
- ответственность не заканчивается на merge в `main`: команда доводит изменение до рабочего состояния в проде и следит за его последствиями
- разработка и эксплуатация работают как одна система: вместе проектируют деплой, мониторинг, алерты, rollback и аварийные процедуры
- цель — одновременно держать две метрики:
  1) быстро и безопасно доставлять изменения
  2) удерживать стабильность сервиса (SLO/доступность/MTTR)

Как это выглядит на практике:
- фича считается завершенной, когда есть не только код, но и метрики, логи, health-check, алерты и понятный план отката
- после релиза команда проверяет результат по наблюдаемости
- инциденты разбираются как дефект системы, а не как вина конкретного человека: фиксируются действия, которые предотвращают повторение

Признаки здорового DevOps-процесса:
- инфраструктура и конфигурация в репозитории (Infrastructure as Code)
- CI/CD-пайплайн с автоматическими проверками
- мониторинг, алертинг, логирование и трассировка
- короткий feedback loop (быстро понять, что сломалось и где)
- постмортемы без поиска виноватых, с фиксацией системных улучшений

### DRY (Don't Repeat Yourself)
Смысл: знание о системе должно храниться в одном месте.

Где применяется:
- общие Terraform-модули вместо копирования `main.tf` по окружениям
- шаблоны CI (`include`, reusable workflows) вместо дублирования одинаковых job
- единые Helm chart values/overrides вместо копирования манифестов

Риск при нарушении DRY:
- изменения надо делать в 5-10 местах, часть мест забывается
- поведение окружений начинает расходиться

### KISS (Keep It Simple, Stupid)
Смысл: выбирать самое простое решение, которое закрывает задачу сейчас.

Практика:
- если достаточно одного сервиса и PostgreSQL, не поднимать микросервисы + Kafka “на вырост”
- если можно использовать managed-сервис, не собирать сложный self-hosted стек без необходимости
- избегать сложных bash-скриптов там, где есть стандартные инструменты IaC

Проверочный вопрос:
- можно ли объяснить решение новому инженеру за 10 минут

### YAGNI (You Aren't Gonna Need It)
Смысл: не реализовывать функциональность “на всякий случай”.

В DevOps это:
- не проектировать избыточную multi-region схему без бизнес-требования
- не добавлять сложный service mesh, если команда пока не столкнулась с его задачами

### SOLID / SRP в инфраструктурном коде
Хотя SOLID родом из ООП, отдельные принципы полезны и в IaC.

Наиболее применимый — SRP (Single Responsibility Principle):
- модуль сети отвечает только за сеть
- модуль БД — только за БД;
- модуль Kubernetes — только за кластерные объекты

Итог:
- проще тестировать
- проще переиспользовать
- меньше побочных эффектов при изменениях

### GitOps как практическое продолжение DevOps
Состояние системы описано в Git, а доставка изменений идет через merge/pull request.

Плюсы:
- прозрачная история изменений
- воспроизводимость
- удобный rollback через Git-историю

## Идемпотентность

Идемпотентность — это свойство операции давать один и тот же итоговый результат при повторных запусках.

Формально:
- запустили действие 1 раз -> получили состояние X
- запустили то же действие еще 10 раз - состояние осталось X, без побочных эффектов

### Примеры

Неидемпотентно:
```bash
echo "10.0.0.5 db.local" >> /etc/hosts
```
Каждый запуск добавляет новую строку.

Идемпотентно:
```bash
grep -q "10.0.0.5 db.local" /etc/hosts || echo "10.0.0.5 db.local" | sudo tee -a /etc/hosts
```

Еще примеры:
- `mkdir /opt/app` — неидемпотентно без проверки (упадет, если каталог есть);
- `mkdir -p /opt/app` — идемпотентно;
- `ln -s target link` — может упасть при повторе;
- `ln -sfn target link` — переустановит ссылку в нужное состояние.

## ContainerD, CRIO

`containerd` и `CRI-O` — это контейнерные runtime, которые Kubernetes использует для запуска контейнеров через интерфейс CRI (Container Runtime Interface).

Что важно понимать:
- `kubelet` не запускает контейнеры напрямую;
- `kubelet` общается с runtime по CRI (gRPC);
- runtime уже использует низкоуровневые компоненты (`runc`, namespaces, cgroups, overlayfs).

### containerd
- универсальный runtime от CNCF;
- может использоваться и вне Kubernetes;
- хорошо поддерживается экосистемой и часто является дефолтом.

### CRI-O
- runtime, заточенный именно под Kubernetes и CRI;
- обычно минималистичнее по возможностям вне k8s;
- часто используется в дистрибутивах, где важна “k8s-only” модель.

Практически: оба варианта корректны для продакшена. Выбор обычно определяется стандартом платформы, требованиями безопасности и экспертизой команды.

## Тесты безопасности в Linux и Docker

Проверки безопасности лучше строить по слоям: хост, образ, контейнер в рантайме, CI/CD.

### 1. Linux-хост
- проверка базовой конфигурации (SSH, firewall, sudo, audit);
- регулярное обновление пакетов и ядра;
- проверка открытых портов и лишних сервисов.

Инструменты:
- `lynis`, `openscap`, `auditd`, `fail2ban`, `nftables`/`iptables`.

### 2. Docker-образы
- сканирование CVE в base image и зависимостях;
- проверка Dockerfile на небезопасные паттерны;
- контроль секретов.

Инструменты:
- `trivy image`, `grype`, `docker scout`, `hadolint`, `gitleaks`/`trufflehog`.

### 3. Runtime-контроль контейнеров
- запуск не от root;
- drop capabilities;
- read-only root filesystem (где возможно);
- seccomp/apparmor/SELinux.

### 4. CI/CD-политики
- сборка блокируется при критичных CVE;
- обязательный lint Dockerfile;
- подписание артефактов и контроль provenance/SBOM;
- admission policy в кластере (например, OPA Gatekeeper/Kyverno).

Минимальный практический набор:
- scan Docker image + lint Dockerfile на каждый merge request;
- nightly scan реестра образов;
- отчеты по критичным уязвимостям и SLA на исправление.

## Control Plane и Data Plane Kubernetes

`Control Plane` управляет желаемым состоянием кластера, `Data Plane` (worker-ноды) исполняет рабочую нагрузку.

### Control Plane
- `kube-apiserver`: входная точка API;
- `etcd`: хранилище состояния кластера;
- `kube-scheduler`: назначает Pod на ноды;
- `kube-controller-manager`: reconciliation-контроллеры;
- (опционально) `cloud-controller-manager`.

### Data Plane (Worker)
- `kubelet`: агент ноды;
- runtime (`containerd`/`CRI-O`);
- `kube-proxy` (или eBPF dataplane в зависимости от CNI);
- CNI-плагин (Calico/Cilium/Flannel и т.д.).

Идея простая:
- Control Plane принимает решения;
- Data Plane выполняет эти решения.

## Какие компоненты запущены на master-ноде и worker-ноде? Почему так?

Термин “master” исторический, сейчас чаще говорят “control-plane node”.

### На control-plane ноде
- `kube-apiserver`;
- `etcd` (в большинстве kubeadm-кластеров локально);
- `kube-scheduler`;
- `kube-controller-manager`;
- `kubelet`, runtime и сетевые компоненты как база ноды.

### На worker-ноде
- `kubelet`;
- runtime (`containerd`/`CRI-O`);
- `kube-proxy` или его замена;
- CNI-агенты.

Почему так:
- компоненты управления изолируют на control-plane ради безопасности и предсказуемости;
- worker-ноды оставляют для пользовательских Pod;
- в production control-plane обычно реплицируют (3+ узла) для отказоустойчивости.

## Когда нет kunernetes, то как его запустить?

Если Kubernetes еще нет, способ запуска зависит от цели.

### Локальная разработка
- `minikube`;
- `kind` (кластер в Docker);
- `k3d` (k3s в Docker).

### Пилот/стейдж/прод в своей инфраструктуре
- `kubeadm` (классический “vanilla” путь);
- Kubespray (Ansible-автоматизация);
- RKE2/k3s (упрощенная эксплуатация).

### Managed Kubernetes
- AWS EKS, GKE, AKS, Yandex Managed Kubernetes и т.д.

Если задача учебная или лабораторная, обычно выбирают `kubeadm` или `kind`. Если бизнес-прод и нет жестких ограничений, чаще выгоднее managed-вариант.

## Написать md-файл, что происходит при отправке kubctl apply development вплоть до рабочего состояния в деталях

Ниже подробная цепочка для команды:

```bash
kubectl apply -f development
```

### 1. Клиентский этап (`kubectl`)
- `kubectl` читает манифесты из `development`;
- валидирует YAML/JSON и определяет типы ресурсов;
- формирует HTTP-запросы в `kube-apiserver`.

### 2. Аутентификация и авторизация
- API Server проверяет, кто отправил запрос (сертификат, token, OIDC и т.д.);
- затем проверяет права через RBAC/ABAC/Webhook.

### 3. Admission chain
- mutating admission может дописать поля (например, default values, sidecar-инъекции);
- validating admission проверяет политики и ограничения.

Если ресурс не прошел политику, запрос отклоняется сразу на этом этапе.

### 4. Запись желаемого состояния
- API Server сохраняет объект в `etcd`;
- ресурс получает `resourceVersion`, UID и метаданные.

### 5. Reconciliation контроллеров
- соответствующий controller “видит” новый объект;
- для `Deployment` создается/обновляется `ReplicaSet`;
- `ReplicaSet` создает нужное число `Pod`.

### 6. Планирование Pod
- scheduler выбирает подходящую ноду по ресурсам, affinity, taints/tolerations, topology constraints;
- в Pod появляется `nodeName`.

### 7. Подготовка Pod на worker
- `kubelet` получает назначение;
- через CRI просит runtime создать sandbox и контейнеры;
- CNI настраивает сетевой namespace и IP;
- CSI (если есть тома) подключает хранилище;
- образы подтягиваются из реестра.

### 8. Запуск и проверки готовности
- контейнеры стартуют;
- `startupProbe`/`livenessProbe`/`readinessProbe` начинают работать;
- пока `readinessProbe` не успешен, Pod не попадает в endpoint’ы сервиса.

### 9. Service discovery и балансировка
- `Service` выбирает готовые Pod по label selector;
- EndpointSlice обновляется;
- kube-proxy/eBPF dataplane обновляет правила маршрутизации;
- DNS (CoreDNS) отдает имя сервиса.

### 10. Стабильное рабочее состояние
- Deployment достигает состояния `Available=True`, `Progressing=True`;
- фактическое число реплик равно желаемому;
- трафик идет только на Ready Pod.

### 11. Что происходит дальше постоянно
- controllers непрерывно сравнивают desired state и current state;
- при падении Pod ReplicaSet создает новый;
- при изменении манифеста `apply` запускает новый цикл reconcile.

Ключевая идея Kubernetes: это не “запустили один раз”, а постоянное автоматическое выравнивание системы к желаемому состоянию.

## Как поднять через kubeadm?

Типовой сценарий (single control-plane + worker):

### 1. Подготовка узлов
- установить совместимые версии `kubeadm`, `kubelet`, `kubectl`;
- установить runtime (`containerd`);
- включить необходимые kernel-параметры (`br_netfilter`, `ip_forward`);
- отключить swap (или настроить по требованиям версии).

### 2. Инициализация control-plane
```bash
sudo kubeadm init --pod-network-cidr=<CIDR_CNI>
```

### 3. Настройка kubectl на control-plane
```bash
mkdir -p $HOME/.kube
sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config
```

### 4. Установка CNI
Применяется манифест выбранного плагина (Calico/Cilium/Flannel).

### 5. Подключение worker-нод
На control-plane:
```bash
kubeadm token create --print-join-command
```
На worker:
```bash
sudo kubeadm join <control-plane-ip>:6443 --token ... --discovery-token-ca-cert-hash sha256:...
```

### 6. Проверка
```bash
kubectl get nodes -o wide
kubectl get pods -A
```

Если все системные Pod в `Running`, кластер готов.

## Как еще можно поднять kubernetes?

Кроме `kubeadm`, распространенные варианты:

Выбор зависит от: среды (локально/облако/on-prem), требований к SLA и зрелости команды эксплуатации.

## Основные команды и как они работают

Базовый рабочий набор `kubectl`:
- `kubectl get <resource>` — получить список/состояние;
- `kubectl describe <resource> <name>` — детальное описание + события;
- `kubectl apply -f <file|dir>` — привести состояние к манифесту;
- `kubectl delete -f <file|dir>` — удалить ресурсы;
- `kubectl logs <pod>` — логи контейнера;
- `kubectl exec -it <pod> -- <cmd>` — выполнить команду в контейнере;
- `kubectl rollout status deployment/<name>` — отслеживать rollout;
- `kubectl rollout undo deployment/<name>` — откат rollout;
- `kubectl scale deployment/<name> --replicas=N` — изменить число реплик;
- `kubectl top pod|node` — метрики CPU/RAM (нужен metrics-server);
- `kubectl get events --sort-by=.lastTimestamp` — события.

Как это работает в общем:
- `kubectl` отправляет REST-запросы в `kube-apiserver`;
- API Server валидирует/авторизует;
- далее контроллеры и kubelet приводят реальное состояние к желаемому.

## Какую задачу решает Helm и почему?

`Helm` решает задачу пакетирования, параметризации и версионирования Kubernetes-манифестов.

Почему это важно:
- вручную поддерживать десятки YAML по окружениям сложно;
- нужны повторяемые установки и предсказуемые обновления;
- нужны rollback и единый способ конфигурирования.

Что дает Helm:
- Chart как “пакет приложения”;
- `values.yaml` для параметров окружений;
- templating без копипасты;
- release-история и `helm rollback`.

По сути Helm в Kubernetes играет роль пакетного менеджера и стандартизирует поставку приложений.

## Как посмотреть events, журнал событий и где они хранятся?

### Как смотреть события
```bash
kubectl get events -A --sort-by=.lastTimestamp
kubectl describe pod <pod-name> -n <ns>
```

### Где события хранятся
- события — это Kubernetes-ресурсы типа `Event`;
- хранятся в `etcd` (как и другие API-объекты);
- имеют TTL и очищаются через event garbage collection.

Важно:
- `Event` не заменяет полноценные логи;
- для расследований нужны также логи приложений, логи нод и audit-логи API Server.

### Журналы компонентов
- `kubelet`: `journalctl -u kubelet`;
- control-plane статические Pod: `kubectl logs -n kube-system <pod>`;
- контейнеры приложений: `kubectl logs`.

## Что такое сетевой плагин? Зачем он нужен? Что он делает? Почему отдельно?

Сетевой плагин в Kubernetes обычно называют CNI-плагином (Container Network Interface).

Зачем нужен:
- Kubernetes сам по себе не реализует контейнерную сеть “из коробки”;
- CNI обеспечивает связность Pod-to-Pod, Pod-to-Service и egress/ingress.

Что делает CNI:
- выделяет Pod IP;
- настраивает маршруты/overlay/encapsulation;
- применяет сетевые политики (если поддерживаются);
- интегрируется с kubelet при создании/удалении Pod.

Почему отдельно:
- сеть в разных инфраструктурах сильно различается;
- модель плагина позволяет выбрать реализацию под задачу (Calico, Cilium, Flannel и т.д.);
- это уменьшает связанность ядра Kubernetes и ускоряет развитие сетевых решений.

## Что такое сервис и как он реализуется?

`Service` в Kubernetes — это стабильная сетeвая абстракция для группы Pod.

Что решает:
- Pod-ы эфемерны и могут пересоздаваться с новыми IP;
- Service дает постоянный DNS-имя и виртуальный IP (ClusterIP).

Как реализуется:
- Service выбирает Pod через label selector;
- API формирует EndpointSlice с актуальными backend-адресами;
- kube-proxy (или eBPF dataplane) на нодах настраивает правила маршрутизации/балансировки.

Основные типы:
- `ClusterIP` — доступ внутри кластера;
- `NodePort` — публикация через порт ноды;
- `LoadBalancer` — внешний балансировщик (в облаке/интеграции);
- `ExternalName` — DNS-алиас на внешний ресурс.

## Что будет, когда он упадет?

Если под “он” имеется в виду Pod приложения:
- Deployment/ReplicaSet заметит падение;
- будет создан новый Pod, пока число реплик не восстановится;
- если настроены `readinessProbe`, трафик не пойдет в нездоровый Pod.

Если падает контейнер внутри Pod:
- kubelet перезапускает его согласно `restartPolicy`;
- при частых падениях возможен `CrashLoopBackOff`.

Если падает worker-нода:
- Node Controller пометит ноду `NotReady`;
- Pod на этой ноде исключаются из Service endpoint’ов;
- workload пересоздается на других нодах (если есть ресурсы и нет жестких ограничений).

Если падает control-plane-компонент:
- при single control-plane кластер может стать частично/полностью недоступным для операций управления;
- в HA-конфигурации отказ одного узла обычно переживается, пока есть кворум `etcd` и доступный API Server.

Итог: отказоустойчивость в Kubernetes достигается репликацией, health probes, правильными лимитами и многозонной архитектурой.
